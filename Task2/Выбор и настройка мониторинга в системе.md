# Задание 2. Мониторинг

## Мотивация

Система состоит из множества приложений и БД.
Компоненты достаточно тесно связаны друг с другом. Отказ практически любого из компонентов может парализовать работу
системы.
Это может привести к:

- ухудшению клиентского опыта, ухудшения репутации,
- потере важных контрактов, финансовым потерям,
- остановке работы операторов и обработки заказов,
- потере/повреждению данных, как следсвие невозможности выполнения заказов и тд.

Как следствие, мониторинг работы системы - одна из самых главных областей, при разработке и поддержке приложений.
Мониторинг предоставляет возможность:

- оперативно реагировать на проблемы в работе системы, повышение трафика, повышенную утилизацию ресурсов и тд.
- выявлять узкие места
- контролировать работу системы с помощью прикладных метрик, например оценивать количество успешных и неуспешных
  результатов обработки.

## Выбор подхода к мониторингу

Для технического мониторинга работы серверов приложений и серверов БД будем использовать метод USE.
Так как он лучше всего работает с ресурсами, производительность которых снижается при интенсивном использовании.

Для остальных компонентов системы будем использовать метод RED.
Этот метод наиболее распространён для распределённых приложений. Метрики RED измеряют показатели, которые важны
для конечных пользователей, а также для сервисов. Обычно используются для мониторинга HTTP-трафика,
может дать ценную информацию о производительности операций ввода-вывода (например, базы данных, вызовов внешних
сервисов).

## Метрики

- Number of dead-letter-exchange letters in RabbitMQ - будет полезна, чтобы понимать какое количество задач
  отклонилось от штатной обработки, в качестве ярлыка можно добавить оригинальную очередь из которой было перенаправлено
  сообщение.
- Number of requests (RPS) for internet shop API - отслеживаем частоту запросов, понимаем какая нагрузка идет на
  систему.
  Ярлык - ендпоинт к которому идет запрос.
- Number of requests (RPS) for CRM API - отслеживаем частоту запросов, понимаем какая нагрузка идет на систему.
  Ярлык - ендпоинт к которому идет запрос.
- Number of requests (RPS) for MES API - отслеживаем частоту запросов, понимаем какая нагрузка идет на систему.
- Number of requests (RPS) per user for internet shop API - будет полезна для обнаружения аномалий, Ярлык - ид
  пользователя
- Number of requests (RPS) per user for CRM API - будет полезна для обнаружения аномалий, Ярлык - ид пользователя
- Number of requests (RPS) per user for MES API - будет полезна для обнаружения аномалий, Ярлык - ид пользователя

- CPU % for CRM API - утилизация ЦПУ, важно для мониторинга производительности. Ярлык - хост сервера
