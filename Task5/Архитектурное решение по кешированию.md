# Задание 5. Кеширование

Для кеширования подходят следующие компоненты системы:
- CRM API и Shop API при взаимодействии с Shop DB - можем кешировать :
  - информацию о заказах, которая часто используется для просмотра и обработки заказа, 
  - товары, доступные для заказа
  - также дополнительную справочную информацию, которые используют сервисы в своей работе
- MES API при взаимодействии с MES db - кешировать информацию о заказах

## Мотивация

На текущий момент в системе наблюдается низкая скорость работы. 
Система кеширования позволит снизить нагрузку на БД, что увеличит быстродействие,
а также уменьшить количество обращений к БД и медленному дисковому пространству, 
что сократит время на накладные расходы и уменьшит общее время процессов и скорости обработки заказов.

## Предлагаемое решение

У нас две проблемы:
- Операторы жалуются на низкую скорость работы
- Новые клиенты недовольны скоростью выполнения заказа
Клиентское кеширование не решит эти проблемы, так как они связаны с быстродействием сервера.

Будем использовать серверное кеширование. За основу возьмем паттерн Cache-Aside и Redis, 
как наиболее простой, надежный и не требующий специальных компетенций от инженеров сопровождения.
К тому же использования паттернов, когда сам кеш ответственен за синхронизацию кеша и базы данных (Read-Through, Write-Through, Write-Behind)
могут снизить надежность системы, на текущий момент нужно наоборот увеличивать надежность.

В качестве инвалидации кеша будем использовать стандартный механизм с TTL, 
причем время жизни будем выставлять гибко для разных данных:
- редко изменяющаяся справочная информация - несколько часов
- динамические данные от нескольких секунд до нескольких минут,
в зависимости от частоты использования и от критичности использования неактуальнной информации.

Также будем использовать явную инфалидацию из прикладного кода для данных, которые всегда должны быть актуальными:
- Запасы товаров
- Цены
- Статусы заказов

Такой гибридный подход к инвалидации позволит сократить количество запросов к БД, 
при этом всегда держать в кеше актуальную инфомрацию для чувствительных данных.

###  Чтение списка заказов:

- Пользователь запрашивает список заказов
- Запрос уходит на server
- поиск в redis GET orders:user:123
  - если данных нет:
    - запрос в БД SELECT * FROM orders WHERE user_id = 123
    - получаем данные Returned 5 orders
    - Добавление данных в redis SET orders:user:123
    - возвращаем данные пользователю
  - если данные есть:
  - возвращаем данные пользователю

### Изменение статуса заказа:

- Оператор выполняет операцию по изменению статуса
- Запрос уходит на server
- Обновление статуса заказа:
  - begin transaction 
  - UPDATE orders SET status = MANUFACTURING_APPROVED where id = 123
  - инвалидация кеша Redis: DEL orders:order:123
  - end transaction
- ответ об успешном обновлении статуса
