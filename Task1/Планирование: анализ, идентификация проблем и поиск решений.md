# Ход работы:

## Анализ схемы, идентификация проблем:

- Каждое приложение имеет по одному инстансу. Отказ практически любого из компанент, 
приведет к остановке всей системы и недоступности для всех пользователей.
- Как вытекающее из первого, нет никаких gateway-API шлюзов для распределения нагрузки, 
фильтрации или блокировки чрезмерного трафика
- Базы данных имеют один инстанс, который работает на запись и на чтение. Это приведет к чрезмерной нагрузке на сервер БД,
что приведет к длительным запросам -> таймаутам -> ошибкам -> повышению запросов от пользователей -> отказу системы.
- Отсутствие очереди для MES API для внешних пользователей. При такой архитектуре чрезмерное количество запросов 
приведет к отказу системы. При этом для внутренней обработки используется RabbitMQ между CRM API и MES API, 
что способствует стабилизации при обработке внутренних заказов.
- Отсутствие дополнительных очередей (Kafka), для длительных задач.
- Много функция на один компонент. Например, Shop API, тут и создание заказов, и обработка всех запросов с UI,
и загрузка изображений, как следствие взаимодействие с двумя независимыми хранилищами данных. Узкое место.
- Статусная модель заказа не предусматривает никаких статусов ошибок. 
Не понятно, заказ действительно в работе или был какой-то сбой.
- По схеме и из описания, можно сделать вывод, что также и нет какого-либо оркестратора,
который бы контролировал (Saga) и по необходимости "допинывал" зависшие заказы.
- Отсутствие кеширование и cdn. Все статические и часто запрашиваемые данные каждый раз запрашиваются из БД.
- Отсутствие мониторинга, и как следствие, отсутствие понимания о нагруженности компонентов системы.
- Отсутствие централизованной системы логирования. Невозможность оперативного решения проблем и выявления ошибок обработки заказов.
- Отсутствие трейсинга. 
- Отсутствие георезервирования.

## Инициативы:

- Увеличение количества инстансов каждого приложения, минимум по 3, для предотвращения недоступности всей системы.
- Введение gateway-API, Service discovery, балансировщиков нагрузки, для распределения запросов между инстансами.
- БД делаем кластерными, внедряем реплики. Далее можем внедрить CQRS, распределить нагрузку на чтение и запись.
- Добавляем очередь для внешних пользователей и внутренних длительных задач.
- Разделяем перегруженные функционалом компоненты на несколько приложений, 
например Shop API можно разделить минимум на 3 разных МС.
- Расширяем статусную модель заказов, добавляем статус ERROR с описанием, 
возможно разных видов статуса ошибки, в зависимости от "этапа" обработки. Клиент должен понимать, что с заказом, возможно,
есть проблемы, чтобы предпринять соответствующие действия.
- Введение Saga, например добавление оркестратора, который будет согласовывать работу приложений,
как следствие, "допинывать" зависшие заказы.
- Добавляем cdn и кеширование для оптимизации работы приложений и снижения нагрузки на БД.
- Внедрение системы единой системы мониторинга.
- Внедрение централизованной системы логирования.
- Внедрение системы трейсинга запросов.
- Организация георезервирования, необходимо развернуть дополнительные инстансы приложения на разных ЦОД. Возможно сделать честный StandIn.

так как неизвестна точка отказа, а улучшить сразу всю систему - достаточно дорого.

Сначала необходимо провести анализ, поэтому:

После проведения анализа и выявления узких мест, необходимо усилить слабые места продукта:
3. Введение gateway-API, Service discovery, балансировщиков нагрузки, для распределения запросов между инстансами.
4. Увеличение количества инстансов каждого приложения, минимум по 3, для предотвращения недоступности всей системы.

Для улучшения производительности и пользовательского опыта:

Для дополнительного мониторинга, оптимизации работы системы и выявления проблем:
9. Внедрение системы трейсинга запросов.

Далее вносим дополнительные изменения в жизненный цикл самого приложения:
10. Расширяем статусную модель заказов, добавляем статус ERROR.
